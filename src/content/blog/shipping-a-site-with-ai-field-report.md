I shipped a production website today. Stack: Astro 6, Tailwind v4, Azure Static Web Apps on the free tier, Cloudflare for DNS and analytics, Terraform for the infrastructure. The site has a valid TLS certificate on a real custom domain, scores 98/100 on Lighthouse desktop and a perfect 100 on three of four mobile categories, ships an OG image generated by a script I didn't write line-by-line, and costs zero dollars per month at rest. From the first commit to a working soft launch took about a Saturday's worth of focused work.

I am not a frontend developer. I am an IT infrastructure leader, and I had AI assistance the whole way through.

There is a particular kind of writing about AI-augmented development right now that goes: "I gave the AI my idea, and it built the thing." I want to write the other piece — the one where the AI built most of the thing, but I had to make every meaningful decision, debug three subtle failures the AI confidently caused, and spend an hour on one bug because the AI was wrong in a way that looked right. That story is more useful, especially for people running IT organizations who are trying to figure out where AI fits in their actual operations.

This is the field report version. One day, one site, three real bugs, and a frame for thinking about what AI-augmented infrastructure work looks like when the demos are turned off.

---

## The workflow that got it done

I used two AI surfaces in tandem. One — call it the planner — held the architecture, the decision log, and the operational walkthroughs. It helped me pick the stack, work through trade-offs, write the project brief, walk me through Azure portal steps when the UI was unfamiliar, and catch drift between what I said I was going to do and what I was actually doing six hours later. The other — call it the implementer — sat inside my code editor with full filesystem access. It wrote files, ran builds, applied Terraform, opened pull requests, and pasted back diffs and terminal output for review.

The division of labor mattered more than I expected going in. The planner kept context across the whole arc. The implementer kept context across the codebase. Asking either one to do the other's job degraded the output noticeably. By the second hour I'd settled into a rhythm: I'd discuss with the planner what I wanted next, sometimes argue with it, agree on an approach, then hand off a concrete instruction to the implementer with enough context that it could just execute. The planner would suggest the verification checks; the implementer would run them and report back; I'd read the result and decide whether we were done.

The AI is not a pair programmer in this setup. The closer analogy is a very fast junior engineer with infinite patience and a real risk of confidently doing the wrong thing. The work the human has to do is judgment, decision-making, and verification. The AI absorbs the typing and the documentation lookup, which together account for more time on an infrastructure project than most people who haven't done one in a while remember.

That setup also means that when something goes wrong, you usually find out quickly. The AI's failures tend to be loud — a deploy fails, a test errors out, a curl returns 404. The exceptions to that pattern are the ones worth writing about, because they're where the time actually goes.

## Story 1: The literal `-`

The first deploy failed with `deployment_token provided was invalid`.

I was using the GitHub CLI to set the deployment token from a Terraform output into a GitHub Actions secret. The instruction the AI generated for me looked like this:

```
terraform output -raw api_key | gh secret set AZURE_STATIC_WEB_APPS_API_TOKEN --body -
```

That's a recognizable shell pattern. The hyphen as the value of `--body` is supposed to mean "read from standard input." It works that way in many CLI tools — `tar`, `kubectl`, `openssl`, plenty of others. So when the AI wrote it, I didn't think twice about it. The pipe sends the token to stdin; the `--body -` reads stdin; the secret gets set.

Except the GitHub CLI doesn't honor that convention. `gh secret set --body -` stores the literal string `-` as the secret's value. The pipe gets ignored. The deploy then tries to authenticate with the string `-` as the API token, and Azure correctly tells it to leave.

The fix is to either omit the `--body` flag entirely (which makes `gh` read from stdin by default) or to pass the value via process substitution:

```
terraform output -raw api_key | gh secret set AZURE_STATIC_WEB_APPS_API_TOKEN
# or
gh secret set AZURE_STATIC_WEB_APPS_API_TOKEN --body "$(terraform output -raw api_key)"
```

Cost of the failure: maybe ten minutes. The deploy log said the token was invalid; I checked the secret in the GitHub UI; the value showed as encrypted but I could see from the secret's character count that something was off; I tested setting the secret manually with the omitted-flag pattern; the next deploy worked.

The lesson isn't that the AI was lazy or inattentive. The lesson is that AI-generated CLI commands can look correct because they follow a convention from a different tool. There is no robust way to know in advance which tools follow the stdin-with-`-` pattern and which don't. The defense is to verify any command that touches a secret, especially when the secret will be opaque downstream.

## Story 2: The semantic flip

The second failure was a deploy that completed but produced a site that returned 404 on the homepage.

The Azure Static Web Apps GitHub Action takes three configuration values that govern where it looks for your built site: `app_location`, `output_location`, and a boolean `skip_app_build`. The standard documentation pattern, the one that shows up first when you search, looks like this:

```yaml
app_location: "/"
output_location: "dist"
skip_app_build: false
```

That tells the action: my source lives at the repo root, I want you to build it for me using the built-in Oryx builder, and the build's output goes to `dist`. Reasonable defaults; works for a lot of projects.

I wasn't using Oryx. I'd already run `npm run build` in the workflow before the deploy step, which is the cleaner pattern when you want full control over your build environment. To skip the action's built-in build, you set `skip_app_build: true`. The AI-generated config looked like this:

```yaml
app_location: "/"
output_location: "dist"
skip_app_build: true
```

That's the bug. When `skip_app_build` is true, the action ignores `output_location` entirely and treats `app_location` as the prebuilt artifact folder. So the action was looking for `index.html` at the repo root, didn't find it (because it was in `dist`), and shipped an empty site.

The correct config under `skip_app_build: true` is:

```yaml
app_location: "dist"
skip_app_build: true
# no output_location at all
```

Cost of the failure: about fifteen minutes. The deploy log was unhelpful; the site was 404; I had to read the action's source on GitHub to figure out the actual semantics.

The lesson here is similar but distinct. When a tool has multiple configuration paths — Oryx-builder versus skip-build, in this case — AI tends to merge them rather than picking one cleanly. The most-documented combination of fields gets retained even when one of them is ignored under the chosen mode. The defense is to read the tool's source when the documentation is silent on the interaction between flags. The AI cannot do this for you reliably yet.

## Story 3: The silent validation

The headline story is the one where I lost an hour.

To put a custom domain on Azure Static Web Apps, you create a TXT record at your DNS provider that proves you own the domain. Azure App Service — the older, larger sibling product — uses the convention `asuid.{domain}` for this record. So if I'm validating `coreymark.com`, the App Service expects a TXT record at `asuid.coreymark.com`.

That's the convention I knew. That's the convention the AI generated when I asked it for the DNS record to add. So I added the TXT record at `asuid.coreymark.com` in Cloudflare and triggered the validation.

Azure responded with `status: Validating, errorMessage: null`.

It stayed that way for forty-four minutes.

There is no timeout. There is no explicit failure. There is no log that says "we looked up the TXT record and it wasn't where we expected." Azure just polls. Quietly. Indefinitely.

I burned the first cycle on hypotheses. Maybe Cloudflare had cached a negative DNS lookup; maybe CNAME flattening at the apex was interfering with the TXT lookup; maybe the propagation delay was longer than usual because the domain had migrated nameservers earlier that week. Each hypothesis got tested. Each test was a Terraform `-replace` cycle and another wait.

The fix turned out to be one of the most embarrassing bugs I've ever burned an hour on. Azure Static Web Apps does not use the App Service convention. It expects the TXT record at the apex of the domain itself — `coreymark.com`, hostname `@`. The Azure portal's Custom Domain details panel said this plainly. It showed `Host: @` in the UI, exactly where you'd expect to read the validation requirement. I just hadn't looked, because I was so confident I knew where the record went.

I noticed it when I was looking at the screenshot I'd asked the planner about. The portal showed `Host: @`. Cloudflare showed `asuid`. The mismatch was visible the whole time.

I moved the TXT record to the apex. The validation cleared in under two minutes. The certificate issued shortly after.

The lesson, and this one matters, is that AI is most dangerous when conventions conflict and it picks one confidently. The wrong-but-plausible answer is much costlier than an answer that hedges with "I'm not sure if Static Web Apps follows the same convention as App Service — check the portal." The AI doesn't tend to volunteer that hedge unless prompted. The defense is to treat any AI-suggested pattern that depends on a "convention" with skepticism, especially when the failure mode of the wrong choice is silent.

## What these have in common

All three failures share a shape. The AI produced an answer that was plausible, that followed the form of the right answer, and that was wrong in a way that wasn't obvious until something downstream broke. None of them were the kind of mistake that a syntax checker or a lint rule would catch. All three were behavioral mismatches between what the human reasonably expected and what the tool actually did.

That shape is going to be the dominant failure mode of AI-augmented infrastructure work for the foreseeable future. The AI will get the syntax right almost every time. It will pick the wrong tool, the wrong flag interpretation, or the wrong convention often enough to matter. The cost will be measured in debugging time, not in obviously broken code.

The implication for IT operators is concrete: don't measure AI ROI in lines of code generated, and don't let your team measure their own productivity that way either. Measure it in elapsed time from intent to working artifact, and budget honestly for the debugging surface that shifts from "writing the code" to "verifying what the AI's code actually does." For a one-person personal-site build, that surface is small enough to absorb. For a multi-person team shipping production infrastructure, the verification discipline needs to scale with the AI usage, or the time savings disappear into longer outages.

## What AI did well

Crediting where credit is due, the things AI assistance was unambiguously good for today:

It moved fast. The Astro scaffold, the Tailwind v4 token system, the layout components, the content collection schema, the RSS feed, the sitemap, the OG image generator script — these would have taken me the better part of a week to write from scratch and get right. The implementer wrote them all in the time it took me to read them and approve. None had bugs that survived the first verification pass.

It enumerated decisions I'd have skipped. When we were picking the stack, the planner walked through trade-offs I'd have hand-waved past — why Astro over Next.js, why Azure Static Web Apps over Vercel, why Terraform for two resources, why Cloudflare proxy on but full-strict TLS — and surfaced cost and operational implications I'd have caught later, after they bit me. That's a real contribution: the AI is good at surfacing what you'd otherwise discover too late.

It maintained state across a long session. I worked on this for hours with breaks. The planner's project brief became the single source of truth for what we were doing and why. When I came back from lunch, I didn't have to reload the context manually; the document had it. The implementer, similarly, kept the codebase in a coherent state across many sequential edits and rebuilds.

It caught regressions a tired human would miss. The OG image was 404'ing on every page until the implementer ran a curl check and noticed. The Lighthouse audit caught a contrast failure on the dark theme that I would have considered "fine" because it looked fine to my eyes. These are exactly the kinds of catches that make AI augmentation worth the verification overhead — they're the things humans get tired of checking by the eighth hour.

## The shape of the work in 2026

Here is what AI augmentation looks like for IT operators right now, stripped of marketing language: the AI does most of the typing, the human does most of the deciding, and the time savings are real but conditional on the human staying engaged enough to catch the AI's confident-but-wrong moments.

That isn't a hype claim and it isn't a doom claim. It's a working description of a tool, useful for the work I do, with edges sharp enough that I'd be cautious about handing it to a less experienced engineer without scaffolding. The IT organizations that get the most value out of this generation of tooling are the ones whose practitioners stay in the decision loop and treat the AI's output as a draft to verify, not an answer to accept.

I will be doing more of this kind of work. The next piece in this series is a deeper look at the AI-augmented build behind my morning briefing system — a smaller project than the website, but one that runs on a daily schedule and surfaces a different set of operational lessons. The two together start to sketch what an IT operator's working relationship with AI looks like in practice, which is the thing I most wish someone had written for me a year ago.

The demos will keep improving. What they can't give you is calibrated intuition about what this technology actually does and doesn't do, in your hands, on your work. That's what a Saturday like this one builds. It's the prerequisite for every larger decision that follows.
